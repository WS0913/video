摘  要

电厂巡检场景通常具有设备分布范围大、现场环境复杂、部分区域不适合人员长时间停留等特点。传统人工巡检虽然方式成熟，但存在巡检效率受人员经验影响明显、异常画面难以及时共享、危险区域进入成本较高等问题。在本课题的实际开发过程中，我将“让巡检机器人现场画面能够稳定、低延迟地回传到浏览器端”作为核心目标，围绕视频采集、设备接入、在线状态维护和网页端监控四个环节，完成了一套端到端无线视频传输系统的设计与实现。
针对项目实现需求，系统采用分层结构进行搭建。机器人侧采集端基于Python开发，负责摄像头接入、设备注册、周期性心跳上报以及视频推流；后端服务基于FastAPI实现，主要承担用户认证、设备管理、在线状态维护和接口调度等任务；流媒体部分采用MediaMTX，负责接收视频流并向浏览器侧分发；前端监控平台采用Vue3、TypeScript、Pinia和Element Plus开发，实现登录、设备查看、多分屏实时监控和基础参数设置等功能。为了使各模块在联调时更容易定位问题，系统中将“业务数据链路”和“视频媒体链路”分开处理：设备注册、用户登录等信息通过HTTP接口交互，视频画面则通过WHIP/WHEP和WebRTC链路传输。
在实际实现过程中，本文重点解决了三个方面的问题：一是采集端设备如何在启动后自动接入平台，并保持在线状态可见；二是浏览器端如何以较低延迟看到机器人侧实时画面；三是在无线网络波动时，系统如何尽量降低卡顿和断流现象。为此，采集端在启动后会先向服务器注册设备，再根据返回的设备标识构造推流地址，同时启动心跳线程持续上报状态；前端播放端则依据设备编号拼接WHEP地址拉取对应视频流，实现设备管理与视频播放之间的统一关联。围绕弱网场景，系统还结合连接状态监听、重连处理和参数调整思路，对视频连续性进行了针对性优化。
从当前项目完成情况来看，系统已经打通了“采集端注册—视频推流—服务端管理—网页端播放”的核心闭环，能够满足毕业设计原型验证与基础演示需求。该系统对于电厂巡检机器人远程监控场景具有一定工程应用价值，同时也为后续接入智能识别、告警分析和多机器人协同管理功能预留了扩展空间。

关键词：巡检机器人；实时视频传输；WebRTC；MediaMTX；FastAPI；Vue3；设备在线管理

 

ABSTRACT

This project focuses on real-time video return for inspection robots in power plants. In practical inspection work, operators need to know not only whether a device is online, but also whether the live picture can be viewed in time and with acceptable delay. To address this requirement, an end-to-end wireless video transmission system is designed and implemented around the current project code.
The system adopts a layered structure composed of a camera client, a back-end service, a media service and a Web monitoring client. The camera side is developed in Python and is responsible for device registration, heartbeat reporting and WHIP-based video publishing. The back end is built with FastAPI to provide user authentication, device management and online status maintenance. MediaMTX is used as the independent media layer for stream ingestion and WHEP distribution. The browser side is implemented with Vue3 and TypeScript, and provides login, device viewing, multi-screen live monitoring and basic settings.
In the implementation process, the project focuses on three practical issues: how to make field devices join the platform automatically, how to connect device identity with video paths, and how to keep the monitoring page usable when the connection becomes unstable. The current system has completed the core closed loop from device registration and heartbeat maintenance to stream publishing and browser playback, and can be used for prototype verification and functional demonstration.

Keywords: Inspection Robot; Real-time Video Transmission; WebRTC; MediaMTX; FastAPI; Vue3; Device Online Management

第1章   绪   论

1.1  课题背景与研究意义
电厂属于典型的连续运行工业场景，现场设备数量多、分布范围广，巡检路线往往穿过高温、高压、强噪声以及电磁干扰较明显的区域。传统人工巡检虽然在很多场合仍然有效，但随着设备规模扩大和安全要求提高，其局限性也越来越明显。人工巡检通常依赖固定路线和人工经验，发现异常后还需要通过对讲、电话或照片等方式再进行信息回传，这种方式不仅存在时间差，而且在复杂现场中容易出现信息表达不完整、异常画面留存不及时等问题。对于一些不适合人员长时间停留的区域，巡检频次和巡检质量也会受到明显限制。
随着移动机器人、嵌入式平台、无线通信和浏览器实时通信技术的不断发展，使用巡检机器人替代人工进入现场已经成为较有代表性的应用方向。机器人搭载摄像头后，可以在巡检过程中连续输出现场视频，使控制中心人员不必到达设备旁边也能看到当前画面。对于运维工作来说，视频并不只是“辅助资料”，而是判断设备外观状态、识别明显异常、确认巡检结果的直接依据。因此，一个真正可用的巡检机器人系统，除了要能移动、能采集，还必须解决视频如何稳定回传、如何低延迟播放以及如何把设备状态纳入统一管理的问题。
本课题正是在这样的工程背景下展开。结合当前项目的实际开发过程，我将“端到端视频链路是否打通”和“现场设备状态是否能够在平台中清晰呈现”作为系统设计的两个重点。项目采用三层结构：采集端运行在机器人或边缘设备侧，负责摄像头接入、设备注册、心跳上报和视频推流；服务端承担业务接口、设备状态维护和系统配置管理；浏览器端提供多分屏实时监控界面，供值班人员查看在线设备和现场画面。与只讨论传输协议或播放器的单点式方案相比，本课题更关注从“设备启动”到“网页可见”的完整过程，也更贴近毕业设计中真实工程实现的要求。
在本项目实现中，采集端主程序启动后并不是直接推流，而是先完成日志初始化和设备注册，再根据设备编号构造WHIP地址并与MediaMTX建立推流连接。服务端则通过FastAPI提供设备注册、心跳、列表查询和认证等接口，并利用后台监控任务定期检查设备最后一次心跳时间，避免页面中出现“画面已经断开但设备仍显示在线”的问题。前端监控页面支持1分屏、4分屏、9分屏和16分屏布局，用户可以从在线设备列表中选择目标设备，播放器根据设备编号构造WHEP地址完成拉流。这些实现细节说明，本课题不是停留在理论设计层面，而是已经围绕当前项目完成了关键链路的搭建与验证。
本课题的研究意义主要体现在以下两个方面。
第一，工程实践意义较为明显。对于电厂巡检场景而言，远程值班人员最关心的是“能不能及时看到现场”和“看到的是否是当前真实状态”。如果视频延迟过高、卡顿严重或设备状态显示不准确，就会直接影响巡检判断效率。通过构建端到端视频传输系统，可以把巡检机器人采集到的现场画面直接送达浏览器监控端，减少人工往返，提高异常确认效率，也能在一定程度上降低人员进入危险区域的频次。
第二，系统设计方法上具有一定参考价值。本文不是单独讨论WebRTC、FastAPI或Vue3中的某一个技术点，而是将设备接入、媒体传输、状态维护和页面展示组织成一个完整系统。对于类似的工业视频项目，这种分层思路具有较好的借鉴意义：业务接口与视频链路分离、设备管理与播放路径统一标识、采集端与前端通过同一设备编号建立关联，这些做法都能够提升系统可维护性和后续扩展能力。
因此，围绕电厂巡检机器人开展端到端无线视频传输系统设计，不仅具有现实应用价值，也有助于加深对实时视频系统工程实现方法的理解。

1.2  国内外研究现状
实时视频传输技术已经广泛应用于安防监控、远程会议、无人机图传、工业机器人、智慧交通和远程医疗等场景。不同应用场景对视频系统的要求并不完全相同：有的更重视大规模分发能力，有的更重视兼容性，而巡检机器人场景则更强调低延迟、稳定性和设备可管理性。传统方案中，RTSP常用于摄像头到流媒体服务器之间的实时传输，协议成熟、接入设备多，但浏览器原生支持较弱；HLS具有良好的网页兼容性和分发能力，但由于分片机制带来的固有延迟，通常更适合直播观看而不是实时巡检；RTMP在早期网页直播中应用广泛，但近年来在低延迟和现代浏览器兼容方面逐渐暴露出限制。
近年来，WebRTC由于具备低延迟、浏览器原生支持、拥塞控制和安全传输等特点，在实时交互式视频场景中得到广泛关注。国外相关研究起步较早，除了视频会议之外，WebRTC也被逐步应用于无人系统画面回传、远程机器人控制、边缘视频接入等方向。随着WHIP和WHEP等接入机制逐渐明确，设备侧推流和浏览器侧拉流不再必须依赖复杂的自定义信令服务器，这使得WebRTC更容易用于工程化部署。部分国外方案已经开始将媒体服务器、边缘节点和自适应传输策略结合起来，以提高复杂网络环境下的播放连续性。
国内在工业视频监控、巡检机器人和智慧电厂等方面也开展了较多工程实践。当前较常见的思路包括：使用传统安防协议进行设备接入，再通过转码服务供网页播放；使用HTTP-FLV、HLS等方式进行网页展示；或直接采用WebRTC实现低延迟预览。不同方案各有优缺点。传统安防体系兼容性较强，但链路较长、部署复杂；HLS方案实现简单，但时延较高；WebRTC方案虽然在接入和调试上更复杂一些，但在“实时看画面”这一核心目标上更具优势，因此逐步成为机器人视频回传和工业低延迟监控的重要选择。
从已有研究和工程实践来看，当前仍存在几个共性问题。第一，很多系统更关注视频是否能传输，却对设备注册、心跳、在线状态维护等管理环节重视不足，导致平台层与媒体层之间联系不够紧密。第二，弱网场景下的视频稳定性仍然是难点，特别是在机器人移动、遮挡变化和局域网信号波动条件下，传输质量容易快速下降。第三，不少方案在论文或设计中偏重原理介绍，但缺少与实际项目代码、部署方式和联调过程紧密结合的说明。
本课题在吸收已有研究思路的基础上，更强调结合当前项目进行系统实现。一方面，项目没有单纯停留在播放器选型或协议比较上，而是围绕“设备上线—推流接入—页面选择—实时播放”完整链路进行设计；另一方面，系统选择MediaMTX作为独立流媒体服务，由FastAPI负责业务管理，由Vue3前端负责页面展示，整体上形成了职责相对清晰的结构。对于毕业设计而言，这种做法的意义在于，不仅能够说明所选技术的合理性，也能够用实际代码证明系统确实可以运行起来。
1.3  研究内容与技术路线
1.3.1  研究内容
本文的主要研究内容包括以下几个方面。
（1）分析电厂巡检机器人实时视频传输的业务需求。围绕巡检机器人远程监控场景，分析用户登录、设备注册、设备在线状态维护、实时预览和弱网恢复等功能需求，并进一步归纳系统的实时性、稳定性、可扩展性和可维护性要求。
（2）设计系统总体架构。系统采用前后端分离模式，分为摄像头采集端、后端服务、流媒体服务和Web监控端四个部分。摄像头端负责采集与推流，后端负责设备和用户管理，MediaMTX负责视频流接入与转发，前端负责展示设备列表和播放实时视频。
（3）实现核心功能模块。后端基于FastAPI和SQLAlchemy实现认证、设备管理、心跳检测和视频状态上报，采用SQLite轻量级数据库存储用户和设备信息；摄像头端基于Python、OpenCV、aiortc等技术在树莓派5平台上实现视频采集和推流；前端基于Vue3、Vite、TypeScript、Pinia和Element Plus实现交互界面；流媒体服务基于MediaMTX完成WebRTC接入。
（4）设计弱网自适应降级与恢复方案。系统在弱网条件下优先保证视频连续性，通过基于心跳检测的分档降级机制，在网络质量下降时降低分辨率、帧率和码率，并在网络恢复后逐级回升。具体策略为：连续心跳失败1次切换到weak档位，连续失败3次切换到poor档位，连续成功后恢复到good档位。系统通过重建推流连接应用新的编码参数，同时配合心跳超时检测和播放端自动重连等方式提高传输稳定性。
（5）开展系统测试与结果分析。通过功能测试、弱网专项测试和基础性能观察验证系统是否满足设计目标，并对端到端时延、播放稳定性等指标进行分析。
1.3.2  技术路线
本文采用“需求分析—总体设计—详细实现—系统测试—总结优化”的技术路线。首先根据电厂巡检机器人业务场景提取系统需求；然后确定前后端分离架构和基于WebRTC的低延迟传输方案；接着分别实现采集端、后端、流媒体服务和前端客户端；随后在局域网和弱网环境下进行功能测试与基础性能观察；最后总结系统成果与不足。

第2章 相关技术与理论基础

2.1  前后端分离架构
本项目采用前后端分离架构组织系统功能。前端负责页面展示、用户交互和状态呈现，服务端负责业务接口、身份校验、设备管理和数据维护，二者通过HTTP接口交换业务数据。这种方式的优点在于页面逻辑与业务逻辑边界清晰，便于分别开发、调试和部署。
在当前项目中，前端基于Vue3、TypeScript和Pinia实现，主要承担登录、设备查看、实时监控和系统设置等页面功能；服务端基于FastAPI实现，主要负责用户认证、设备注册、心跳接收、状态维护和接口返回。视频画面不经过服务端中转，而是交由独立的流媒体服务处理。这样做可以避免业务接口和视频数据相互干扰，也更符合实时视频系统的工程实现习惯。
因此，前后端分离在本课题中的意义，不只是提高开发效率，更重要的是让“业务链路”和“媒体链路”保持相对独立：服务端专注于管理设备和用户，前端专注于展示和操作，视频传输则由流媒体服务专门承担。
2.2  流媒体传输相关技术
2.2.1  WebRTC 协议
WebRTC是一套面向实时音视频通信的技术体系，具有低延迟、浏览器原生支持和拥塞控制等特点[2][12]。对于电厂巡检机器人场景来说，监控人员更关注现场画面是否能够及时显示，因此WebRTC在低时延方面的优势较适合本课题需求。与以分片播放为主的传统网页视频方案相比，WebRTC更适合承担实时监控任务。
在本项目中，WebRTC的价值主要体现在两个方面：一是浏览器端无需安装额外播放器即可直接接收实时视频；二是在网络发生波动时，连接层本身具备一定的适应能力，有利于维持基本可用性。虽然WebRTC的接入和调试复杂度高于普通HTTP视频播放，但对于“尽快看到现场画面”这一目标而言，它更符合本课题需求。
2.2.2  WHIP/WHEP 接入机制
WHIP和WHEP分别用于WebRTC流的推送和拉取[8][9]。WHIP主要解决设备侧如何以HTTP方式把本地WebRTC媒体流送入流媒体服务，WHEP则解决浏览器端如何以统一方式从流媒体服务拉取对应视频。与传统自定义信令方式相比，这两种接入机制明显降低了工程实现复杂度。
结合当前项目实现，采集端在注册成功后会根据device_id构造WHIP地址，把摄像头画面推送到MediaMTX；浏览器端则依据同一device_id构造WHEP地址并完成播放。这样做的好处是，设备身份与视频路径天然绑定，前端不需要关心采集端内部细节，只需要根据设备编号即可定位到目标视频源。

2.3  系统开发技术
2.3.1  FastAPI后端框架
FastAPI是基于Python的现代异步Web框架，支持类型提示、数据校验和自动生成接口文档[3]。在本项目中，FastAPI非常适合承担服务端角色：一方面可以较快完成登录、设备注册、心跳和查询等接口开发，另一方面其异步特性也适合处理持续存在的设备接入请求。对毕业设计项目而言，FastAPI兼顾了开发效率和工程可读性。
2.3.2  Vue3+Vite前端框架
Vue3适合构建组件化页面，Vite则适合快速搭建和调试前端项目[6]。当前项目中的登录页、设备管理页、实时监控页和系统设置页都建立在这一技术组合之上。再配合TypeScript和Pinia，可以让页面交互、状态管理和接口调用保持较清晰的结构，这对后续维护和论文说明都比较有利。
2.3.3  MediaMTX流媒体服务
MediaMTX是一个轻量级流媒体服务，支持多种协议接入和分发[5]。本项目选择它作为独立流媒体服务，主要原因是它能够直接承接WHIP推流和WHEP拉流，使采集端、服务端和前端之间形成清晰的媒体链路。采集端负责送流，浏览器负责拉流，服务端只负责设备和用户管理，整个系统的职责边界因此更加明确。
通过引入MediaMTX，项目避免了在服务端内部自行处理复杂媒体转发逻辑，也降低了整体实现难度。这种设计使本课题能够把更多精力放在设备接入、状态维护和页面监控这些更贴近业务的问题上。


第3章 系统需求分析

3.1  系统建设目标
本课题的系统建设目标，不是单纯完成一路视频播放，而是结合电厂巡检机器人的实际使用方式，搭建一套从设备接入、状态维护到浏览器端实时查看都能够闭环运行的端到端无线视频传输原型系统。结合当前项目代码实现，系统建设目标可以概括为以下几个方面。
第一，实现巡检设备的快速接入。机器人或固定摄像头所在的采集端在启动后，应能够自动向平台注册设备信息，包括设备名称、设备类型、安装位置和网络地址等内容。注册成功后，系统需要为该设备建立唯一标识，并使后续心跳上报、视频推流和前端播放都围绕这一标识展开，避免出现“设备信息与视频流无法对应”的问题。
第二，实现低延迟实时视频预览。对于电厂巡检场景来说，值班人员最关心的是能否及时看到机器人当前所处位置的真实画面，因此系统需要尽量缩短从采集端到浏览器端的传输链路。结合本项目实现，系统以WHIP推流、WHEP拉流和WebRTC播放作为主要低延迟方案，目标是在局域网和较稳定无线网络环境下完成可用的实时预览。
第三，实现设备在线状态可视化。视频系统在实际使用中不能只显示画面，还必须告诉用户设备是否在线、心跳是否正常、当前是否可被选择播放。本项目在服务端增加了设备注册、心跳、设备列表查询和后台离线检测逻辑，目标就是让监控人员不仅能“看到视频”，还能够“知道设备当前是否可用”。
第四，实现适合值班场景的Web监控界面。当前项目不是面向单路测试，而是面向实际监控使用习惯，因此前端页面需要支持设备列表查看、在线状态筛选、多分屏显示、视频窗口切换以及基础系统设置等功能。这样可以使一个浏览器页面同时承担“查看设备”和“查看现场”的双重任务。
第五，为后续弱网优化和功能扩展预留空间。电厂巡检机器人在移动过程中可能遇到无线网络波动，因此系统至少要具备连接状态感知、异常提示、基础重连和状态上报能力。虽然当前项目仍以原型验证为主，但在结构设计上已经为网络等级上报、参数调整和后续AI识别接口预留了扩展位置。
3.2  业务场景分析
本系统面向的核心业务场景，是电厂巡检机器人在现场执行巡检任务时，将第一视角视频画面回传到监控中心，供值班人员进行远程观察和辅助判断。与普通网页视频播放不同，这一场景具有几个明显特点：设备是移动的、网络条件会变化、现场环境复杂、值班人员更关注实时性而不是历史浏览。因此，在业务流程设计上，系统必须把“设备接入”和“实时播放”紧密结合起来。
结合本项目的运行流程，典型业务场景如下：机器人上电后，采集端程序首先初始化日志和本地摄像头，再向后端平台发起设备注册请求。注册成功后，采集端获得设备唯一标识，并立即启动心跳线程，持续向服务器上报设备仍然在线。与此同时，采集端根据设备标识拼接WHIP地址，与MediaMTX建立推流连接，把现场视频送入流媒体服务。这样，设备业务信息和视频流路径就通过同一个device_id关联起来。
在监控中心侧，值班人员通过浏览器进入系统登录页面，输入账号密码后进入主界面。进入设备管理页面后，可以查看当前所有设备的名称、类型、位置、IP地址和在线状态；进入实时监控页面后，可以根据需要选择1分屏、4分屏、9分屏或16分屏布局，并从在线设备中选择目标机器人进行播放。播放器根据设备编号构造WHEP地址，从MediaMTX拉取对应视频流并在页面中展示。对于值班人员来说，这一过程不需要理解底层推流协议，只需要关心“设备是否在线”和“画面能否正常显示”。
在无线网络较稳定时，系统可以较顺畅地完成上述流程；而在机器人移动到遮挡区域或信号较弱位置时，视频播放可能出现加载变慢、短时中断或状态异常。针对这一情况，当前项目通过心跳机制、连接状态提示和前端播放器错误反馈，尽量让用户及时知道问题出在哪里：如果设备仍在线但视频暂时异常，更可能是媒体链路波动；如果设备心跳中断并被服务端判定为离线，则说明采集端或网络连接已经发生较明显故障。
3.3  功能需求分析
3.3.1  用户登录与权限管理需求
系统首先需要具备基础登录能力，避免未授权用户直接访问设备信息和实时画面。结合当前代码，后端提供登录、获取当前用户信息、退出登录和修改密码等接口，前端则在登录成功后保存访问令牌，并通过统一请求封装在后续访问中自动携带认证信息。对本项目而言，这一功能不仅用于保护系统，也用于保证设备管理页面、监控页面和系统设置页面的访问边界清晰。
此外，用户信息不仅要能用于身份校验，还要能够在页面中体现当前登录者的基本资料，例如用户名、角色和创建时间。这样做的目的并不是扩展复杂权限系统，而是让整个平台具备最基本的运维管理属性。当前项目已具备管理员登录和密码修改流程，为后续扩展为多角色权限控制提供了基础。
3.3.2  设备注册与在线状态管理需求
设备管理是本系统区别于普通网页播放器的重要部分。采集端启动后必须先进行设备注册，否则前端即使能拉流，也无法知道当前画面对应的是哪一台机器人。结合当前项目实现，注册时至少需要上传设备名称、设备类型、位置和IP地址，后端根据IP进行去重处理：如果识别到是同一设备重新上线，则更新原有记录；如果是新设备，则创建新的设备条目并生成对应标识。
注册完成后，设备还需要维持持续在线状态，因此系统必须具备周期性心跳功能。采集端通过固定时间间隔向后端发送心跳请求，后端收到后更新最后心跳时间，并把设备标记为在线。若在设定阈值内未再收到心跳，后台监控任务应自动将设备置为离线。这个需求在工程上非常关键，因为如果没有离线检测，前端列表中就可能长期保留失效设备，影响用户判断。
3.3.3  实时视频预览需求
实时预览是系统面向值班人员的核心功能。首先，用户应能从在线设备中选择任意一路视频源进行观看，而不是输入固定地址手动播放。其次，系统应支持多分屏布局，以适应同时查看多台机器人或多个摄像头的使用需求。再次，播放器在加载流失败、设备离线或连接异常时，需要给出明确反馈，而不是只显示空白画面。
从本项目实现来看，前端播放器根据设备编号构造WHEP地址完成拉流，页面中还提供全屏和关闭等基本操作。由于每个视频窗口都可能在不同时间被创建和销毁，因此播放器组件还应在卸载时释放资源，避免多路预览时浏览器资源持续增长。由此可见，实时预览需求不仅是“把视频播出来”，还包括窗口管理、错误反馈和资源释放等配套要求。
3.4  非功能需求分析
3.4.1  实时性需求
实时性是本课题最重要的非功能指标之一。电厂巡检人员查看视频的目的，是及时了解当前设备状态，而不是事后回看，因此系统应尽可能减少采集端到浏览器端之间的等待时间。结合当前项目目标，系统在正常局域网条件下应尽量把端到端延迟控制在较低水平，使用户在页面中看到的画面与现场状态基本同步。
为满足这一需求，项目在整体架构上没有让业务后端参与视频数据中转，而是将媒体流直接交给MediaMTX处理，由浏览器通过WHEP直接拉取，从而缩短链路并降低中间处理开销。
3.4.2  稳定性需求
稳定性主要体现在三个方面：一是采集端能否持续运行并稳定上报状态；二是后端能否长期维护设备在线状态；三是浏览器端在连接波动时能否给出合理反馈。当前系统通过日志记录、心跳机制、后台离线检测、播放器加载提示和错误提示等方式，初步满足了这一需求。对于毕业设计原型而言，系统不一定需要在所有极端条件下都保持最佳画质，但至少应做到在异常发生时能定位问题来源，并在网络恢复后继续工作。
3.4.3  可扩展性与可维护性需求
由于本课题后续可能继续扩展智能识别、告警联动和多机器人并发接入等功能，因此系统在结构上需要保持清晰。当前项目中，采集端、服务端、前端和流媒体服务相互独立，职责划分明确；前端采用页面、组件、状态仓库和接口封装分层组织；后端则按照认证、设备、配置和后台任务进行拆分。这种组织方式有利于后续替换单个模块，也方便对不同问题进行单独排查。
3.5  可行性分析
从技术可行性来看，本项目选用的FastAPI、Vue3、MediaMTX、WebRTC、Python和TypeScript等技术都较为成熟，相关文档完善，社区资源丰富，能够支持毕业设计阶段完成系统实现与联调。项目中最关键的低延迟播放问题，采用WHIP/WHEP与MediaMTX组合后，也避免了从零搭建复杂信令服务的额外负担。
从实现可行性来看，当前项目代码已经完成设备注册、心跳检测、登录认证、多分屏监控和基础系统设置等核心模块，说明系统方案不仅停留在设计层面，而是已经能够运行。采集端、服务端和前端均可独立启动，再通过局域网进行联调，符合毕业设计原型系统的实现条件。
从使用可行性来看，前端界面基于浏览器运行，用户不需要安装专用客户端即可查看设备状态和实时视频，操作门槛较低。对值班人员而言，页面化的操作方式也比命令行工具更直观。
从维护可行性来看，当前项目已经具备日志输出、设备状态显示和接口分层能力，后续如果出现设备无法上线、心跳异常或视频无法播放等问题，可以较方便地沿着“采集端—服务端—流媒体—前端”链路逐步排查。因此，从技术、实现、使用和维护四个维度看，本课题具有较好的可行性。

第4章 系统总体设计

4.1  总体架构设计
本系统采用分层设计思想，将整体划分为采集端层、流媒体服务层、业务服务层和Web展示层四个部分。这样的划分并不是为了形式上的完整，而是结合项目开发过程中的实际需要做出的选择：视频媒体流和业务数据流在处理方式上存在明显差异，如果全部堆叠在一个服务中，不仅调试困难，也会增加后续维护成本。
采集端层运行在机器人侧或接入摄像头的边缘设备上，主要负责本地摄像头调用、设备注册、心跳上报以及视频推流。该层的核心任务是把“现场设备”变成“平台中可见、可管理、可播放”的在线节点。流媒体服务层由MediaMTX承担，负责接收采集端推送上来的媒体流，并向浏览器侧提供对应的拉流入口。业务服务层由FastAPI实现，主要处理用户登录、设备管理、状态维护和接口响应。Web展示层则基于Vue3实现，直接面向值班人员，承担设备查看和实时播放等交互任务。
这四层之间的关系可以概括为：采集端把设备信息和视频源送入系统，业务服务层负责记录和维护设备状态，流媒体服务层负责接管媒体数据转发，Web层负责把设备信息和现场画面展示给用户。当前项目的优势在于，业务接口与视频链路彼此解耦，但又通过统一的设备编号进行关联，因此既保证了结构清晰，也保证了实际使用中的一致性。
4.2  模块划分与通信关系
结合当前代码，采集端内部主要由主程序、设备管理器和WHIP推流器组成。主程序负责启动顺序控制和资源清理；设备管理器负责设备注册、心跳循环、在线状态上报和设备下线；WHIP推流器负责创建WebRTC连接、采集摄像头帧并推送到MediaMTX。也就是说，采集端内部已经形成了“业务接入”和“媒体发送”两个相对独立的功能单元。
服务端内部则由认证接口、设备接口、配置接口、数据库模型和设备监控任务组成。认证接口负责登录、登出和获取用户信息；设备接口负责注册、心跳、流状态更新和设备查询；设备监控任务负责定时检查在线设备是否超时；数据库模型负责保存用户和设备基础信息。通过这种模块划分，后端并不直接处理视频帧，而是专注于状态管理和接口服务。
前端部分主要由页面、组件、接口封装和状态仓库组成。页面层包括登录页、实时监控页、设备管理页和系统设置页；组件层中最关键的是VideoPlayer，用于封装WHEP拉流播放逻辑；接口封装层用于统一调用后端API；状态仓库用于保存用户信息、设备列表和本地系统设置。这样做的好处是页面负责交互，组件负责复用，状态仓库负责共享数据，结构较为清晰。
从通信关系上看，系统中存在两条并行链路。第一条是业务链路：采集端通过HTTP接口向后端注册设备并发送心跳，前端通过HTTP接口获取设备列表和用户信息。第二条是媒体链路：采集端通过WHIP向MediaMTX推流，前端通过WHEP从MediaMTX拉流。两条链路虽然彼此独立，但都围绕同一个device_id工作，从而保证了“设备记录”和“视频流地址”始终能够对应起来。
4.3  核心流程设计
4.3.1  设备注册流程
设备注册流程是整个系统建立映射关系的起点。采集端程序启动后，首先读取本地配置，获取设备名称、设备类型、位置和本机IP地址，然后向后端的设备注册接口提交请求。服务端接收到请求后，会先根据IP地址查询数据库，判断这台设备是首次接入还是重新上线。如果数据库中已经存在对应IP的设备，就更新其名称、位置和状态；如果不存在，就创建新的设备记录。
注册成功后，后端返回device_id和stream_url。采集端保存该device_id，并将其用于后续心跳地址和WHIP推流地址的拼接。这样做的设计目的，是让设备注册不只是“登记一个名字”，而是立即建立起“设备身份—流媒体路径—前端播放目标”之间的统一关系。
4.3.2  心跳与在线状态更新流程
设备注册完成后，采集端会启动心跳线程，以固定时间间隔向后端发送心跳请求。心跳请求中不仅包含时间戳，还可携带当前网络等级、往返时延估计和丢包估计等状态字段。后端收到请求后，将设备最后心跳时间更新为当前时间，并把设备状态标记为在线。
为了防止采集端异常退出后设备仍长期显示在线，后端在启动时还会同步启动后台监控任务。该任务定期检查所有在线设备，如果发现某设备的最后一次心跳超过阈值，就自动将其更新为离线。前端设备列表在刷新后即可显示这一变化。该流程的意义在于，即使用户不去查看视频窗口，也能先从设备列表中判断当前哪些节点真正可用。
4.3.3  实时推流与拉流流程
在当前项目中，视频实时传输依赖WHIP推流和WHEP拉流完成。采集端拿到device_id后，构造对应的WHIP地址，创建RTCPeerConnection，并将摄像头视频轨道加入连接中。随后采集端生成本地offer，通过HTTP方式发送给MediaMTX，MediaMTX返回answer后，双方完成会话协商，视频流开始持续推送。
浏览器端播放流程与此对应。用户在监控页面中选择某一路设备后，前端根据设备编号生成WHEP地址，VideoPlayer组件创建播放器实例并向该地址发起请求。如果媒体链路建立成功，页面开始显示实时画面；如果连接失败，则组件显示错误提示。通过这种设计，前端无需了解采集端的内部实现，只要知道设备编号即可完成拉流。
4.4  弱网适应与恢复方案设计
考虑到电厂巡检机器人可能在移动过程中遇到网络波动，系统在总体设计时并没有把弱网问题完全留给底层协议处理，而是从采集端状态上报、服务端设备管理和前端播放反馈三个层面进行了基础考虑。
采集端层面，设备管理器会记录连续心跳成功和失败次数，并维护网络等级、RTT和丢包估计等状态字段。这些信息一方面可通过心跳上报给服务端，另一方面也可通过流状态接口同步给平台。虽然当前项目仍以基础状态上报为主，但它已经为后续更精细的动态参数调节打下了结构基础。
服务端层面，设备接口能够保存网络等级、RTT、丢包率、码率、分辨率和流状态等字段，使后端不只知道设备是否在线，还能知道设备大致处于什么网络状态。前端层面，播放器组件对加载中、超时和连接失败等情况进行了可视化反馈，在页面中能够直接提示“加载中”或“视频流超时”，减少用户误判。
因此，当前系统的弱网设计更适合被理解为“基础可恢复框架”而不是完全成熟的自适应算法：它已经具备状态感知、异常提示和恢复接口，但在后续工作中仍可以继续向自动档位切换和更精细的码率调节方向深化。
4.5  系统安全性设计
4.5.1  用户认证与密码保护
系统采用基于JWT的用户认证方式。用户登录时，后端根据用户名查询数据库，并使用bcrypt校验密码哈希。校验通过后，系统生成访问令牌返回给前端，前端在后续接口请求中携带该令牌访问受保护资源。密码不以明文形式保存，而是经过哈希处理后存入数据库，这样即使数据库被读取，也难以直接还原用户原始密码。
4.5.2  设备接口认证
除了用户登录认证外，采集端访问设备相关接口时还需要携带设备令牌。服务端通过请求头中的X-Device-Token校验采集端身份，只有令牌匹配时，才允许进行设备注册、心跳上报和流状态更新。这一机制的意义在于，避免任意脚本伪造设备接入请求，保证平台中的设备记录具有基本可信度。
4.5.3  CORS跨域访问控制
由于前端和后端在开发阶段通常分开运行，因此系统在服务端增加了CORS中间件配置，用于控制哪些来源可以访问后端接口。开发环境下可以适当放宽，便于局域网调试；正式部署时则应结合实际访问地址进行限制，以减少无关来源调用接口的风险。
4.5.4  流媒体服务配置
MediaMTX作为独立流媒体服务，主要承担媒体接入和分发任务，不直接参与用户鉴权逻辑。当前项目中，它通过配置文件定义服务监听方式和路径接入规则，并与设备编号对应起来。后续若进入更严格的生产场景，还可继续增加推流鉴权、拉流权限控制和HTTPS保护等安全措施。
4.5.5  安全性总结
总体来看，当前系统已经具备三层基础安全措施：用户登录认证、设备接口令牌认证和跨域访问控制。这些措施足以支持毕业设计阶段的原型验证，也为后续进一步增强安全部署提供了可扩展基础。
4.6  数据库与接口设计
当前项目的数据库设计以轻量和够用为原则，主要围绕用户和设备两类核心对象展开。用户表保存登录所需的用户名、密码哈希和角色信息；设备表则保存设备编号、名称、类型、位置、IP地址、在线状态、分辨率、帧率、码率、网络等级、流状态和最后心跳时间等字段。这样的字段设计能够同时满足前端设备列表展示和后端状态维护的需要。
在接口设计上，系统将认证接口和设备接口分开管理。认证接口包括登录、获取当前用户、登出和修改密码；设备接口包括注册、心跳、流状态更新、列表查询、详情查询、手动下线和删除设备。通过这种设计，后端接口既能为前端页面提供数据来源，也能为采集端提供稳定的设备接入入口。
第5章 系统详细实现

5.1  后端模块实现
5.1.1  用户认证模块
后端认证模块主要位于server/api_auth.py中，围绕登录、获取当前用户、退出登录和修改密码四项功能展开。当前实现采用FastAPI自带的OAuth2PasswordBearer机制接收令牌，并结合JWT完成用户身份识别。登录时，系统首先根据用户名查询数据库中的用户记录，再使用bcrypt对输入密码与数据库中的密码哈希进行校验；校验通过后，后端按照配置中的有效期生成访问令牌，并将其返回给前端。前端登录成功后保存令牌，后续访问受保护接口时统一携带。
在实现细节上，get_current_user函数是认证链路中的核心。它会先解码JWT令牌，再从数据库中查询对应用户名的用户记录。如果令牌无效、已过期，或者数据库中不存在该用户，系统都会返回认证失败。修改密码接口则在用户已登录的前提下，先验证旧密码，再将新密码重新哈希后写回数据库。这样的实现方式虽然比较轻量，但已经满足毕业设计阶段对系统访问控制的基本要求。

5.1.2  设备管理与心跳模块
设备管理模块主要位于server/api_devices.py，是服务端最核心的业务模块之一。该模块不仅负责设备注册和设备查询，还负责设备心跳处理、流状态上报、设备下线和删除等功能。与普通设备列表接口不同，本项目中的设备管理模块直接服务于视频监控链路，因此它既要保存设备基础信息，也要维护设备当前的在线状态与视频相关状态。
在设备注册实现中，后端接收采集端上报的设备名称、类型、位置、IP地址以及可选的视频参数。如果系统发现相同IP的设备已经存在，就将其视为重新上线并更新原有记录；如果不存在，则创建新的设备对象。注册成功后，后端返回device_id和stream_url，前者用于后续业务标识，后者用于与流媒体路径建立对应关系。设备心跳接口则负责更新last_heartbeat、status以及可选的network_level、network_rtt_ms和packet_loss等字段。这样一来，后端不仅知道设备是否在线，也能保存一定的网络状态信息。
后台的离线检测逻辑由device_monitor.py完成。该任务在服务端启动时自动运行，每隔固定时间扫描一次状态为online的设备。如果某个设备长时间未更新心跳，就被自动标记为offline。对实际使用而言，这个功能非常重要，因为它解决了“采集端程序异常退出后，平台仍误认为设备在线”的问题。

5.1.3  视频状态与网络状态上报模块
除了基本心跳之外，当前项目还实现了专门的视频状态上报接口。该部分同样位于api_devices.py中，通过`/api/devices/{device_id}/stream-status`接口接收采集端上报的分辨率、帧率、码率、网络等级、RTT、丢包估计、重连次数和流状态等信息。系统会把这些字段写入设备表，并根据重要字段是否变化决定输出详细日志还是普通状态日志。
这一实现说明，服务端在当前项目中并不只承担“设备是否在线”的管理任务，还承担了视频链路状态汇聚功能。虽然当前前端界面未完全展示所有上报字段，但从系统结构上看，这些数据已经具备接入页面展示、测试分析和后续策略控制的基础，后续可以进一步扩展为更细致的网络质量监控功能。
5.2  摄像头采集端实现
5.2.1  设备接入与运行主流程实现
采集端主程序位于camera-client/main.py。结合代码可以看到，程序整体采用异步方式组织，启动过程并不是简单地“打开摄像头然后推流”，而是按照设备管理和媒体传输分阶段执行。具体流程包括：初始化日志系统、创建设备管理器、向服务端注册设备、启动心跳线程、构造WHIP地址、初始化推流器以及保持主循环运行。
设备管理器位于camera-client/device_manager.py，是采集端与平台交互的关键模块。register方法会先获取本机IP地址，再将设备名称、类型、位置和IP封装成请求体发送到后端注册接口。注册成功后，系统保存返回的device_id，并在后续心跳和状态上报中复用该标识。start_heartbeat方法则启动后台线程，以固定时间间隔向后端发送心跳请求。cleanup阶段还会停止推流、停止心跳并调用下线接口，使设备退出过程比较完整。这些实现细节反映出当前项目并非单纯的视频发送程序，而是一个带有平台接入能力的采集端节点。
5.2.2  摄像头采集与WHIP推流实现
视频采集与推流功能主要位于camera-client/whip_streamer.py。该文件中，CameraVideoTrack继承自aiortc的VideoStreamTrack，用于把摄像头采集到的图像帧封装成WebRTC可发送的视频轨道。当前实现中使用Picamera2获取图像帧，再通过VideoFrame.from_ndarray转换为可发送的数据结构，并在每一帧中附带时间戳信息。这样做的作用，是让采集端能够直接把本地摄像头画面接入WebRTC推流链路。
WHIPStreamer负责建立具体的推流连接。启动时，它会创建RTCPeerConnection对象，注册连接状态变化回调，然后创建CameraVideoTrack并将其添加到连接中。系统随后生成本地offer，通过HTTP POST请求把SDP发送到MediaMTX的WHIP端点。只有在MediaMTX返回answer之后，推流连接才算真正建立完成。代码中还尝试为发送端设置最大码率，如果设置失败则退回WebRTC默认拥塞控制。连接建立后，推流状态会通过日志输出，连接失败、断开或关闭时也会触发状态变化回调。
从这一实现可以看出，本项目没有采用传统FFmpeg命令行推流作为主链路，而是直接在Python侧完成WebRTC推流连接建立，这使得采集端在后续做连接状态感知、重建和状态上报时更灵活。

5.2.3  采集端网络状态维护实现
当前项目在device_manager.py中增加了连续心跳成功次数、连续心跳失败次数、RTT估计、丢包估计和network_level等字段。每次心跳发送后，系统会根据请求返回结果更新这些状态：如果心跳成功，就清零失败计数并刷新RTT；如果心跳失败或请求异常，就增加失败次数并更新丢包估计。采集端还实现了report_stream_status方法，用于把当前视频状态和网络状态统一上报给服务端。
需要说明的是，当前代码已经具备“状态感知”和“状态上报”的基础，但并未在主流程中实现完整的自动档位切换算法。因此，本项目在这一部分的实际完成情况应更准确地理解为：已经为后续弱网自适应控制预留接口，并能够把采集端运行状态同步给平台，而不是已经完全实现严格意义上的自动码率自适应。
5.3  流媒体服务实现（MediaMTX）
5.3.1  流接入与分发实现
本项目选择MediaMTX作为独立流媒体服务，其作用不是承载业务逻辑，而是专门负责音视频流的接入与分发。在当前方案中，采集端通过WHIP将视频推送至MediaMTX，浏览器端通过WHEP从同一服务拉取视频。这样做的直接好处是，FastAPI后端不需要处理任何媒体数据，只负责维护设备和用户信息，系统分层更加清晰。
在路径设计上，MediaMTX中的流路径与device_id保持一致。例如，同一设备对应的WHIP入口和WHEP入口都围绕device_id展开。这样一来，前端只要知道设备编号，就能够定位对应视频源；后端也可以把设备管理和视频访问自然绑定起来。
5.3.2  流媒体服务在系统中的配合作用
从工程实现角度看，MediaMTX承担的是“中间媒体层”的角色。它一方面屏蔽了浏览器端直接连接采集端的复杂性，另一方面也使多客户端观看同一路视频成为可能。对于当前毕业设计项目而言，引入MediaMTX的意义不只是降低开发难度，更重要的是让服务端专注于业务接口，让采集端专注于视频生产，让前端专注于页面展示，各部分职责更加明确。

5.4   前端模块实现
5.4.1   登录与设备管理页面实现
前端登录页面负责接收用户名和密码，调用后端登录接口获取访问令牌。登录成功后，前端会把用户状态保存到Pinia仓库中，并跳转到系统主界面。由于前端请求统一通过封装后的request模块发出，因此后续页面访问不需要重复处理认证细节。
设备管理页面位于web-client/src/views/DeviceManagement.vue。页面中使用Element Plus表格组件展示设备名称、设备类型、位置、IP地址、状态和最后心跳时间等字段，并通过筛选框支持按在线状态和设备类型过滤。页面顶部提供“刷新”按钮，用于主动重新获取设备列表。对于在线设备，用户可以点击“查看视频”跳转到监控页面；对于无效或不再使用的设备，可以直接执行删除操作。当前代码还保留了网络等级和视频流状态等扩展列的格式化逻辑，说明设备管理页面在设计上已经考虑了进一步展示运行状态的可能性。

5.4.2 实时预览页面实现
实时预览页面位于web-client/src/views/LiveMonitor.vue，是前端最核心的业务页面。页面顶部提供1分屏、4分屏、9分屏和16分屏切换按钮，中间区域按照当前布局生成对应数量的视频窗口。每个空白窗口都可以点击，随后弹出在线设备选择对话框，用户从中挑选要显示的设备。
设备被选中后，页面会在对应单元格中创建VideoPlayer组件。该组件根据设备编号构造WHEP地址，并使用`@eyevinn/webrtc-player`建立播放器实例。播放过程中，页面可显示加载中遮罩、错误信息、设备名称、分辨率、帧率和在线状态等内容，用户还可以进行全屏查看或关闭该路视频。页面对已选择设备还做了本地缓存，刷新浏览器后能够恢复先前布局，减少重复操作。
从代码实现上看，实时监控页面还支持自动刷新设备列表，并根据系统设置中的刷新间隔定时执行更新。这一设计能够使在线状态变化更快地反映到页面上，提升监控使用体验。

5.4.3 播放器组件实现
播放器组件位于web-client/src/components/VideoPlayer.vue。与页面层不同，该组件只负责具体的视频加载、状态展示和资源清理。组件接收device对象作为输入参数，在挂载时根据device_id拼接WHEP地址，创建WebRTCPlayer实例并执行load操作。若播放器在加载过程中出现超时或连接中断，组件会更新错误提示文本；若媒体恢复，则会清除错误状态。
组件在界面上提供了较完整的播放辅助信息，包括设备名称、分辨率、帧率、在线状态以及全屏和关闭两个操作按钮。更重要的是，在组件卸载时会主动销毁播放器实例，释放连接和浏览器资源。这对于多分屏场景非常重要，因为如果不及时清理，长时间切换设备后浏览器资源占用会持续增加。
5.4.4 系统设置页面实现
系统设置页面位于web-client/src/views/Settings.vue，主要承担基础参数配置和用户信息展示功能。页面中可以修改系统名称、默认分屏布局、是否自动刷新以及刷新间隔等本地设置，这些参数由Pinia中的config仓库统一维护，并同步保存到localStorage。这样一来，用户关闭浏览器后再次进入系统，仍然可以保留之前的使用偏好。
除了基础设置外，系统设置页面还展示当前用户信息，并提供修改密码和退出登录操作。修改密码时，页面会校验旧密码、新密码和确认密码，再调用后端修改密码接口完成更新。整体来看，系统设置页面虽然不直接参与视频播放，但它完善了整个平台的操作闭环，使系统不只是一个“能播放视频的页面”，而是一个具备基本管理能力的监控平台。
第6章 系统测试与结果分析

6.1 测试环境与测试方法
为验证系统是否能够完成预期功能，本文在局域网环境下对当前项目进行了联调测试。测试环境主要包括一台开发主机、运行采集端程序的设备、普通摄像头、MediaMTX流媒体服务、FastAPI后端服务以及Chrome浏览器。测试时按照“先启动MediaMTX，再启动后端，再启动前端，最后启动采集端”的顺序进行，确保设备注册、推流接入和页面播放可以串联起来。
考虑到本课题属于工程原型实现，测试重点放在功能可用性和运行现象观察上，而不是做过于理想化的实验室精密测量。因此，本文主要采用黑盒测试和联调观察相结合的方法，对登录、设备接入、在线状态更新、多分屏播放和异常恢复等内容进行验证。
6.2 功能测试
6.2.1 登录与设备管理功能测试
首先对登录功能进行验证。输入正确的管理员账号和密码后，系统能够成功进入主界面；输入错误密码时，后端返回认证失败信息，前端不允许继续访问受保护页面。测试结果表明，当前认证链路可以满足平台基础访问控制要求。
随后对设备接入流程进行测试。启动采集端程序后，设备会自动向后端发起注册请求，服务端成功返回device_id，前端刷新设备管理页面后可以看到新增设备信息，包括设备名称、类型、位置、IP地址和在线状态。停止采集端后，随着心跳中断，服务端后台监控任务会在超时后将设备标记为离线。说明设备注册、心跳维护和离线检测链路已经打通。
设备管理页面的筛选和删除功能也进行了验证。用户可以按在线状态和设备类型过滤设备，并可对不再使用的设备执行删除操作。从结果来看，页面交互和后端接口响应基本一致，能够满足原型系统日常管理需要。
6.2.2 实时预览功能测试
实时预览测试主要验证前端是否能够根据设备编号正确拉取视频流。测试中，用户进入监控页面后可切换1分屏、4分屏、9分屏和16分屏布局，并通过弹窗选择在线设备。选择设备后，页面中的VideoPlayer组件会根据device_id构造WHEP地址，随后加载对应视频流。
测试结果表明，在服务端、流媒体服务和采集端均正常运行时，浏览器能够显示实时画面。页面支持全屏查看和关闭当前窗口，刷新页面后也可以恢复部分已保存的设备布局。整体上，实时监控页面已经能够完成多路查看这一核心功能。
6.2.3 异常与恢复功能测试
在联调过程中，还对异常情况下的系统表现进行了观察。当采集端停止推流或网络短时波动时，前端播放器会先进入加载中状态，若连接无法恢复则显示错误提示；当采集端重新启动并恢复推流后，页面可以重新建立播放连接。若设备长时间没有上报心跳，前端刷新设备列表后会看到其状态变为离线。
需要说明的是，当前系统已经具备基础恢复能力，但它更偏向“异常提示+连接重建”的原型实现，尚未形成成熟的自动画质切换策略。因此，本节测试结果主要说明系统具备基本容错能力，而不将其表述为完全成熟的弱网自适应系统。
6.3 联调现象分析
从联调过程来看，当前系统最稳定的链路是“设备注册—心跳维持—页面查看设备状态”，其次是“采集端推流—浏览器端播放”。在局域网条件较好时，视频播放较流畅，页面切换和设备选择响应正常。出现问题时，日志和页面提示也能够帮助定位问题来源，例如是设备未成功注册、心跳中断，还是视频流暂时未建立。
在网络波动或采集端重启场景下，系统表现出一定恢复能力，但恢复时间和画面连续性仍受网络条件影响较大。这说明当前项目已经完成了原型验证所需的关键闭环，但若要进一步面向复杂现场部署，仍需要对网络波动下的细粒度处理进行加强。
6.4 本章小结
本章围绕登录认证、设备管理、实时预览和异常恢复等内容，对系统进行了功能测试和联调分析。测试结果表明，当前项目已经能够完成设备接入、状态维护、视频推流和浏览器播放等核心任务，基本达到毕业设计原型系统的预期目标。同时，测试也说明系统在弱网和长时间稳定运行方面仍有继续优化空间。

第7章  总  结

7.1 工作总结
本文围绕电厂巡检机器人实时视频回传需求，完成了一套端到端无线视频传输系统的设计与实现。与只验证单个播放功能的实验不同，本课题更强调完整链路是否能够跑通，因此在项目实现中同时考虑了采集端接入、设备注册、在线状态维护、流媒体分发以及浏览器端实时监控几个关键环节。
结合当前项目实现，系统已经完成以下主要工作：在采集端实现设备注册、心跳上报和WHIP推流；在服务端实现用户认证、设备管理和后台离线检测；在流媒体层完成视频接入与分发；在前端实现登录、设备查看、多分屏监控和基础设置功能。通过这些模块的协同，系统已经能够实现“设备上线后在页面可见，并可通过浏览器查看实时画面”的基本目标。
7.2 核心成果
本文的主要成果可以概括为三点。
第一，完成了一个面向巡检机器人场景的端到端视频原型系统。它不是单一协议演示，而是把设备管理和视频播放结合起来，形成了较完整的工程闭环。
第二，采用WHIP/WHEP与MediaMTX组合方式完成WebRTC接入，减少了自建复杂信令链路的难度，同时保留了低延迟播放的优势。
第三，在系统结构上实现了设备编号与视频流路径统一，使设备状态管理和前端播放能够自然关联，这一点对后续维护和扩展都比较重要。
7.3 不足与后续展望
虽然当前项目已经完成主要功能，但仍存在一些不足。首先，系统对网络状态的处理还处于基础阶段，当前更多是状态上报、异常提示和恢复接口预留，后续还需要结合RTT、丢包率和码率变化实现更细致的动态调节。其次，当前测试主要在有限设备和局域网环境下完成，多设备并发和长时间运行场景验证还不充分。再次，平台权限控制仍较为基础，后续可继续完善角色区分和接口访问限制。
总体来看，本文完成的系统已经具备较好的原型完整性。后续若继续扩展，可从弱网优化、多设备并发验证、系统安全增强以及智能识别接入等方向深入，使其更接近真实电厂巡检应用需求。

cd server

pip install -r requirements.txt

python -c "from models import init_db; import asyncio; asyncio.run(init_db())"

uvicorn main:app --host 0.0.0.0 --port 8000 --reload
后端服务启动后监听 8000 端口。

cd web-client

pnpm install

pnpm dev
